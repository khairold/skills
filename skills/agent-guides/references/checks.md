# checks: step 4

Both go in the repo, in the project's language, beside its other scripts and tests. Match the
project's style, lint and type rules; they are code like any other.

## The generator

A script in the project's scripts folder (for example `scripts/build_guides.py`). If the project
already has a generator for a map or inventory, extend it instead of adding a second one.

It must:

1. **Read facts from the code,** never from docs: the build tool's list of apps or packages, the
   import graph, models/tables and who writes them, routes, CLI commands, scheduled jobs, env
   vars read, enums. Parse the source (AST) or ask the framework; don't regex prose.
2. **Write only between the markers** of each existing guide, and leave the rest alone:
   ```
   <!-- generated by scripts/build_guides.py: do not edit -->
   ## Owns (generated)
   ...
   <!-- end generated -->
   ```
   A guide without markers gets the block appended. A guide that doesn't exist is not created
   (writing a guide is a human-reviewed step, not a generator's).
3. **Be deterministic:** sorted output, no timestamps, no absolute paths, so an unchanged repo
   gives byte-identical files.
4. **Offer a function** that returns the expected text of every guide without writing, for the
   test below.

Keep the block short: a table or a few bullets per kind of fact. A long inventory belongs in one
map file that the block points at.

## The tests

In the project's test suite, run by its normal check (so they fail in the same place as
everything else). Each has a message that tells the agent what to do.

| Test | Fails when | Message says |
|---|---|---|
| guides are current | a committed generated block differs from what the generator would write | run the generator |
| guide paths exist | a guide names a file or folder path that does not exist | fix the guide |
| guide commands exist | a guide names a CLI or management command, npm script or make target that does not exist | fix the guide |
| every unit has a guide | a unit from the build tool's list has no guide | write its guide |
| the root guide stays short | the root guide has more than 80 lines | move a fact to its folder's guide |
| code carries no build notes | a comment or docstring matches the build-note regex from the survey | say what the code does now; history goes to the decision log |
| the generator touches only its block | the hand-written text around a block changes | (a unit test of the generator's replace function) |

For the build-note test, scan comments and docstrings only (a tokenizer or AST, not a grep of the
whole file), so string values in code are not flagged. Add a small test that feeds it one sample
of each form and one allowed form (`D-42`, a version number), so the regex cannot rot silently.

Where a list of guides is needed (paths test, commands test), read it from one place the project
already keeps: the build tool's list of units, or one constant the generator exports. Never a
second hand-kept list.

Run the generator, then the project's full check, before step 5.
